# CREAO 题面解读与执行方案

> 2026-10-11 初步探索。本文是工作分析，不是最终的 `design-system-guideline.md` 或 `compliance-audit.md`。规则示例是拟制定的规则，不代表 CREAO 已存在这些规定。

## 1. 这道题到底要做什么

题目要求建立一条可追溯的链：**现有设计系统 → 页面组合规则 → 工程与编程智能体的执行约束 → 上线前检查 → 用真实界面证明检查能发现问题。**

需要同时解决两种不同的问题：

1. **组件使用失控：** 已有组件和 tokens，但开发者自行实现相似控件、选择不合适的变体，或者没有遵守交互约定。应建立复用边界和检查机制。
2. **页面组合缺失：** 单个按钮合规，不代表整个页面合理。需要定义页面类型、信息顺序、操作位置、滚动区域、状态与响应式行为。

题目明确只要求两份 Markdown。可把检查规范、示例断言、PR 模板和例外流程写进文档；没有要求搭建新的应用或重写组件库。真正接入 CI 可以是后续工程工作，但提交的机制必须具体到可以实现，不能只有“请设计师审核”或“让 AI 检查”。

## 4. 可用于最终审计的三个初步实例

以下是“观察事实 + 拟定规则”的演示；不声称已经运行仓库 CI，也不声称违反了尚未取得的官方设计系统。

### F-01：文件页缺少语义化页面标题

- **事实：** `/files` 上方“文件”在 DOM 中是 `BUTTON`，页面没有 `h1`、`h2`、`h3` 或 `[role="heading"]`。可访问性树也把它暴露为按钮。对照 `/apps` 和 `/integrations`，它们都有一级页面标题。
- **拟定规则 `LAY-01`：** 每个顶层管理页面必须在主内容区有一个可访问名称与页面身份一致的一级标题。面包屑或返回按钮不能替代它。
- **影响：** 依靠标题导航的用户无法通过页面标题定位文件管理区域；页面外观相似掩盖了结构差异。
- **检查方式：** 在稳定加载的页面中，断言主区域内一级标题恰好一个、可见、名称为“文件”；不能只跑截图差异检查。
- **修复方向：** 保留有实际用途的根目录导航按钮，另用现有排版组件提供一级标题；若没有导航用途，则直接以标题组件呈现。先核对现有组件库再选择实现。
- **边界：** 这是拟定产品规范下的结构问题；不能仅据此宣称已完成 WCAG 合规判定。

### F-02：空状态引导了一个不存在的标签名称

- **事实：** “已连接 (0)”下提示“前往可用标签页连接服务。”，实际标签为“全部 / 可连接 / 内置 / 已连接 (0)”，没有“可用”。
- **拟定规则 `NAV-02`：** 引导文案提到的站内目的地必须与当前语言下实际可见的导航名称一致，且目的地必须存在。
- **影响：** 用户必须自行推断“可用”就是“可连接”。
- **检查方式：** 同一导航名称使用同一个本地化词条；功能测试核对空状态目的地文案与实际标签名称，并验证选择后进入可连接结果。仅检查“翻译 key 存在”不足以发现这个问题。
- **修复方向：** 复用“可连接”标签的本地化名称；最好直接提供“浏览可连接服务”操作。

### F-03：可恢复的空状态缺少就地操作

- **事实：** 智能体空状态提供“创建您的第一个智能体”按钮；已连接空状态内部只有说明，没有链接或按钮，用户必须到上方寻找标签。
- **拟定规则 `STATE-01`：** 当空状态存在用户可执行的恢复步骤时，空状态区域必须提供一个指向该步骤的可操作控件；仅告知“去某处”不够。纯信息状态和无权限状态应另行定义。
- **影响：** 同类空状态的下一步表达不一致，增加寻找成本。
- **检查方式：** 给该状态准备零连接器的数据夹具，定位空状态区域，检查恢复操作可见、可用，并点击验证目标状态。不要用“页面任何地方存在按钮”作为通过条件。
- **修复方向：** 在空状态内复用现有 Button 或 Link，切换到“可连接”标签并保留合理的搜索条件。
- **边界：** 上方已有可用导航，因此不是死路；这是拟定模式下的一致性和效率问题，严重程度低于阻断核心任务。

### 不应过度推断的事项

- 文件页视图切换在可访问性树中显示为 checkbox，但 DOM 实际是带 `aria-pressed` 的按钮，不能根据树的一个标签就认定组件实现错误。此项不列为违规。
- 不同页面有不同宽度、按钮数量或卡片，不必然是问题；必须先确定它们是否承担同一种任务、属于同一种模式。
- 截图无法证明使用了错误 token、错误组件 import 或不合适的源码 API。
- 暂未测量颜色对比度、键盘焦点顺序、窄屏、缩放、真实运行、失败恢复、审批和定时任务流程；这些不能写成通过或失败。

## 5. 官方资料对范围的补充

官方 [Agents 产品说明](https://creao.ai/features/ai-agents) 描述了从成功聊天转成可复用 Agent 的过程；[Agents 文档](https://docs.creao.ai/features/agents) 覆盖结构化输入、详情页、文件、会话、版本和审批。[Scheduled Runs](https://creao.ai/features/scheduled-runs) 涉及频率、时区、下次执行及运行记录。[Dynamic Workflows](https://creao.ai/features/dynamic-workflows) 描述计划审批、执行状态和单任务检查。

这些材料足以帮助决定需要哪些模式，但不等于本轮亲自操作过这些界面。官方产品说明与开发文档对自主模式的默认值还出现不同表述，当前账号显示“总是询问”；不能据此认定所有新账号的默认值。最终规范应要求清晰展示当前模式，而不是把未确认的默认行为写成事实。

## 6. 建议制定的页面模式

先以少量高复用模式覆盖主流程，避免每个功能单独创造模板。以下均为提案，组件的实际名称要在取得现有库后映射。

| 模式 | 适用情形 | 必须定义的结构与行为 |
| --- | --- | --- |
| `P-01 Conversation Workspace` | 聊天、运行中的任务 | 全局导航 → 会话身份与状态 → 消息和执行结果 → 输入区；产物检查区如何展开、滚动和回到对话；审批卡在流程中的位置 |
| `P-02 Collection` | 智能体、文件、连接器集合 | 页面身份 → 页面级操作 → 搜索/筛选/结果数 → 列表或卡片 → 空、加载、失败状态；推荐内容是否允许占用主要管理区域 |
| `P-03 Resource Detail` | 某个 Agent 或一次运行 | 名称、状态及上下文 → 主要操作 → 稳定的标签导航 → 当前内容；运行状态与配置状态要分清 |
| `P-04 Focused Configuration` | 创建 Agent、配置定时任务 | 简短可完成的任务用对话框；需要长表单、跨区参考或可分享 URL 的任务用完整页面；定义字段分组、错误、保存与取消 |
| `P-05 Review and Approval` | 审批计划或外部操作 | 要做什么、影响对象、内容预览、当前状态、批准与拒绝；操作后明确显示真实结果，不能把“已提交”当作“已完成” |

模式选择应按任务判断：主要是在对话中推进任务选 P-01；浏览和筛选同类对象选 P-02；检查单个对象选 P-03；完成有明确终点的配置选 P-04；确认后果选 P-05。审批卡可嵌入会话或详情页，不需要强行成为独立页面。

每个模式都需要写清：必选与可选区域、现有组件映射、操作层级、滚动归属、窄屏折叠顺序、长文本处理、完整状态表、例外条件和检查方法。不要武断规定“全页面只能有一个主按钮”：集合页多个卡片有各自操作时，应按操作区域和任务定义层级。

## 7. 执行机制怎样才算具体

### 规则格式

每条规则使用稳定编号，并包含：适用范围、MUST/SHOULD、可观察要求、理由、合格/不合格例子、检查器、失败条件、严重度和例外方式。

例如 `LAY-01` 的验收应是“顶层管理页主区域恰好有一个名称匹配的可见一级标题”，而不是“页面层次清晰”。

### 三种检查各管一类问题

| 检查层 | 能证明什么 | 不能单独证明什么 |
| --- | --- | --- |
| 源码检查 | 组件 import 来自批准的库；受约束的颜色/间距使用已批准 token；禁止重复造规定已有的基础控件 | 页面可用、布局合理、操作真的成功 |
| 运行时测试 | 标题、名称、焦点、状态转移、空状态恢复、内容不被遮挡；固定数据下的截图回归 | 使用了哪个源码组件；新布局是否应成为标准 |
| 有明确检查项的人工评审 | 模式选择、信息优先级、密度、异常场景、规则例外是否合理 | 代替自动测试或验证未执行的流程 |

AST 检查比简单搜索字符串可靠：需要处理别名、重导出、包装组件与动态样式。视觉回归能发现变化，但基准截图本身也可能不合规，因此必须先审核基准。自动无障碍工具只是补充；并不会自动验证所有产品规则。

### 上线门禁

建议在最终规范中写明如下契约：

1. PR 标明受影响页面、模式 ID、组件库版本、规则版本和状态矩阵。
2. 作者或编程智能体先读取规范与现有组件映射，再实现页面；不得自行创建不存在的 token 或假设组件 API。
3. 必须提交受影响路径的自动检查结果，以及固定视口、固定数据、固定状态的截图。最终选择的视口要结合产品支持范围；当前 943 × 898 只是探索环境，不是正式覆盖矩阵。
4. 阻断级 MUST 失败、必需检查未运行或缺少证据时，不得通过。检查结果区分 PASS、FAIL、NOT TESTED 和有批准记录的 EXCEPTION。
5. 设计师负责模式与体验判断，工程负责人负责检查实现与执行记录；例外要有规则 ID、适用路径、原因、补救措施、负责人和失效日期。编程智能体不能自己批准例外。
6. 旧页面的历史债务单列；新增与本次修改区域遵守新规则，关键任务阻断问题优先处理，避免把全站改造塞进一次功能 PR。

在拿到仓库之前，以上只是可实现的机制设计，不能写成“已经启用分支保护/CI”。不要编造项目中不存在的测试命令。

### 必须证明检查不会误判

建议至少用一个真实违规做负例、一个符合规则的界面做正例。以 STATE-01 为例：连接器空状态应失败，智能体空状态应通过；针对修正后的空状态再验证点击能到达目标。负例被识别不等于整套系统有效，但能证明规则不只是口号。

## 8. 两份正式交付物的推荐组织

### `design-system-guideline.md`

1. 范围、权威来源、已有设计系统的复用边界。
2. 页面模式选择表。
3. 各模式的区域、行为、状态和响应式契约。
4. 编号规则目录与组件映射。
5. 编程智能体的执行步骤及 PR 证据模板。
6. 检查机制、阻断标准、责任人和例外流程。

### `compliance-audit.md`

1. 审计对象清单、访问时间、语言、视口、状态及未覆盖项。
2. 每条发现：截图位置、观察事实、影响、规则 ID、严重度、修复方式。
3. 每条发现的检查入口、输入状态、失败断言及预期输出。
4. 已执行检查与仅设计的检查明确分开；附正例、未确认事项和修复后复验要求。

两份文件通过规则 ID 交叉引用。最终若只能提交两个文件，应把必要的可视证据以允许访问的链接或提交平台支持的形式纳入；不能交付只在本机可用的绝对路径，也不要默认允许多交一个截图目录。

## 9. 推荐的推进顺序

1. **先补材料。** 确认是否存在独立提供的截图、功能简报，以及能访问的组件库或 tokens 文档。最关键的是功能简报，它决定新布局的压力测试。
2. **补齐页面盘点。** 在已授权、不会触发真实任务的前提下观察详情、配置、审批和运行状态；无法进入的状态用明确标注的资料参考，不能伪装成实测。
3. **写可执行的 v1 规则。** 以 4–5 个模式和一组高价值规则为起点，避免大量无法检查的原则。
4. **做真实审计。** 先把本轮三个实例串起，再补组件复用与布局层面证据；不能为了凑数量推断不存在的违规。
5. **用新功能验证泛化。** 将功能简报逐项映射到模式，展示新增区域、状态和例外如何决策。如果没有真实简报，只能将替代案例标为假设演练。
6. **核对提交完整性。** 每条发现有规则和检查方法；每条阻断规则有负责人；所有来源、运行状态和限制准确；两份最终文件中的编号一致。

当前已完成翻译、产品初步探索和解题方案。正式规范、完整合规审计、组件库映射与 CI 接入尚未完成。
